# Harness reference comparison

Reviewed 2026-09-08. These are design references, not imported code or endorsements.
Branch links can evolve; domfx's tracked rules and installed tools remain authoritative.

| Reference                                                                                                                                     | Relevant evidence                                                                                                                             | Application to domfx                                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| [Floating UI README](https://github.com/floating-ui/floating-ui/blob/master/README.md)                                                        | TypeScript/pnpm workspaces, separate core and platform packages, built packages, and interactive browser fixtures with Playwright screenshots | Preserve core/browser separation and exercise the lab as a consumer. The Chromium suite now exercises the existing lab fixtures; broader browser/GPU coverage remains task-specific. |
| [TypeGPU contribution guide](https://github.com/software-mansion/TypeGPU/blob/main/CONTRIBUTING.md)                                           | Issue/discussion-driven scope, pnpm development examples, tests before PR review, and release preparation                                     | Use a scoped brief and the existing lab/check/release workflows. Do not copy publishing shortcuts or enable releases.                                                                |
| [Playwright contribution guide](https://github.com/microsoft/playwright/blob/main/CONTRIBUTING.md)                                            | Explicit package ownership, executable style rules, public API documentation, behavior tests, and hermetic tests                              | Keep conventions executable, update consumer documentation with behavior, and test harness failures locally without GitHub or a model service.                                       |
| [Software Mansion: first steps in mature projects](https://agentic-engineering.swmansion.com/getting-started/first-steps-in-mature-projects/) | Map existing code, plan acceptance checks, anchor changes to suitable examples, review separately, and report real evidence                   | Use a brief → design → implement → verify → review loop with concise context and task-specific references.                                                                           |

The conclusion is our design judgment: a small workflow over existing gates fits this
experimental library better than a general agent scheduler or a new application framework.
The harness cannot guarantee design quality; it makes expectations and evidence inspectable.

## 2026 harness research

| Primary report                                                                                                                                                 | Relevant practice                                                                                                                      | Decision for domfx                                                                                                                                                                 |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [OpenAI: Harness engineering](https://openai.com/index/harness-engineering/) · February 11, 2026                                                               | Short navigation instructions, repository knowledge, executable architectural constraints, and inspectable application behavior        | Keep `AGENTS.md` as a map, retain existing boundary gates, and require browser evidence for rendering. Their large layered architecture is not a template for this library.        |
| [Anthropic: Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps) · March 24, 2026  | Explicit evaluation criteria, structured handoffs, and reassessing orchestration overhead as models improve                            | Add a small continuation record for interrupted tasks; keep a distinct contract review. An always-on planner/generator/evaluator system needs evidence of benefit before adoption. |
| [LangChain: Improving Deep Agents with harness engineering](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering) · February 17, 2026 | Inspect failures, improve verification, and provide useful environment context                                                         | Exercise actual process failures and record runtime identity alongside source and command outcomes. Logs remain local; a tracing service is not needed for these checks.           |
| [LangChain: Better Harness](https://www.langchain.com/blog/better-harness-a-recipe-for-harness-hill-climbing-with-evals) · April 8, 2026                       | Establish a baseline, make targeted changes, test representative cases, and use held-out tasks plus human review to detect overfitting | Use the [evaluation guide](harness-evaluation.md). Passing runner tests proves tooling behavior; skill quality requires separate task trials.                                      |

These are reports from their authors' systems. Their benchmark gains, autonomy levels,
and cost claims do not establish domfx's results. Prefer a reproduced local failure
and a regression over adding another framework or copying every rule from a blog.
